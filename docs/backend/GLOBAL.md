# ERP Backend Global Contract

This document is the source of truth for backend architecture, API conventions, persistence,
tests, and operational behavior.

## 1. Architecture

The service is a modular monolith under `backend/app`:

- `api/`: FastAPI routers and dependency wiring.
- `schemas/`: public Pydantic request and response contracts.
- `services/`: application use cases and transaction boundaries.
- `db/`: SQLAlchemy base, sessions, persistence models, and database adapters.
- `core/`: cross-cutting configuration, errors, middleware, CORS, and request context.
- `utils/`: small framework-independent helpers.
- `scripts/`: explicit maintenance commands.

Dependencies point from HTTP adapters toward application decisions. API schemas must not expose
SQLAlchemy entities directly. A business capability can grow into its own package when doing so
protects a real change boundary; do not create a microservice without an operational reason.

## 2. HTTP API

- Keep liveness at `GET /health` and database readiness at `GET /health/ready`.
- Declare router prefixes, tags, and shared dependencies on `APIRouter`.
- Use one HTTP operation per function and explicit response models or return types.
- Use `Annotated` aliases for reusable FastAPI dependencies.
- Bound pagination, sorting, filtering, request sizes, and external calls when those features are
  introduced.
- Document authentication, authorization, idempotency, and conflict behavior before adding a
  business route.

## 3. Naming and serialization

- API paths use lowercase kebab-case where multiple words are needed.
- JSON fields use `camelCase`.
- Python names and PostgreSQL identifiers use `snake_case`.
- Convert explicitly at schema and persistence boundaries.

## 4. Errors

Expected errors use this JSON envelope:

```json
{
  "message": "Human-readable explanation.",
  "parameter": "optionalCamelCaseField"
}
```

Validation errors use HTTP 400. Use 401 for missing or invalid authentication, 403 for denied
actions, 404 for absent resources, 409 for invariant or concurrency conflicts, and 422 only when
a route deliberately defines different semantic validation. Never leak stack traces or database
details.

## 5. PostgreSQL and transactions

- PostgreSQL is the source of truth. SQLite is not an integration-test substitute.
- Use SQLAlchemy 2 typed mappings and one bounded synchronous session per request or job.
- Application services own transaction scope. Repositories flush when necessary but do not commit.
- Enforce durable invariants with `NOT NULL`, foreign keys, unique constraints, checks, and explicit
  delete behavior.
- Add indexes from actual query shapes. Review query plans before speculative indexing.
- Use UTC-aware timestamps and database-generated defaults for durable records.

## 6. Migrations

- Every schema change requires Alembic.
- Review autogenerated revisions, imports, constraints, indexes, upgrade behavior, and downgrade or
  roll-forward behavior.
- Prefer expand-and-contract changes for deployed systems.
- CI runs `alembic upgrade head` and `alembic check` against PostgreSQL.

## 7. Configuration and secrets

- Configuration comes from environment variables or an untracked `backend/.env` file.
- `backend/.env.example` contains development-only placeholders, never real credentials.
- Do not place secrets in source, tests, migrations, logs, or Postman files.
- Production must provide its own `DATABASE_URL`, CORS allowlist, credentials, and secret references.

## 8. Observability and security

- Every response carries `X-Request-Id`; propagate a valid incoming value or generate one.
- Access logs include method, path, status, duration, and request ID, but no bodies, tokens, or query
  strings.
- Keep CORS origins explicit. Do not use credentialed wildcard origins.
- Validate authentication and authorization separately at resource and action boundaries.
- Parameterize SQL and allowlist any dynamic sort or filter fields.

## 9. Tests and quality

- Unit-test business rules without FastAPI or the database.
- Contract-test routes through `TestClient`.
- Integration-test migrations and persistence against PostgreSQL.
- Mock only external boundaries.
- Before finishing backend work, run the commands in `AGENTS.md` and
  `.cursor/rules/backend-quality.mdc`.

## 10. Deployment status

The application includes Mangum compatibility for a future AWS Lambda path. Hosting, managed
PostgreSQL, IAM, secrets, networking, and deployment workflows are intentionally deferred until an
infrastructure target is selected.
